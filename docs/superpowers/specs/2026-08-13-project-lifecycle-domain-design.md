# C02 Project Lifecycle Domain Design

**Change:** `project-lifecycle-domain`  
**Owner:** zhao  
**Reviewer:** zhang  
**Base:** C01 `platform-backend-foundation`  
**Scope:** Platform V1 domain persistence and state transitions only

## Goal

Persist the first project lifecycle entities and enforce their state transitions in one domain service boundary. A failed, cancelled, orphaned, or merely built Candidate must never replace the current PlayableVersion or create a Release.

## Non-goals

- No Vue route or visual change.
- No AI, OpenGame, AGF, executor, adapter, artifact generation, or build process execution.
- No SSE, queue, workflow engine, worker, resource extraction, Resource Review, or publish UI.
- No business HTTP routes in C02. C03-C07 and C11+ will expose the domain through their own API changes.
- No duplicated `Project.stage` column. Stage is a read model derived from persisted domain state.

## Architecture

```text
SQLAlchemy ORM models
        ↓
Repositories: persistence queries only
        ↓
ProjectLifecycleService: transaction + state transition authority
        ↓
Derived ProjectStage read model
```

The service receives a SQLAlchemy `Session` or transaction context. Routers and future jobs must call service methods; they must not mutate status fields or pointers directly. Repositories may load and save records but do not decide whether a transition is allowed.

## Persisted Model

All entities use opaque UUID strings generated by the backend and timezone-aware UTC timestamps. JSON content is stored as text through a small typed serialization helper; C02 does not introduce a document store.

### Project

`projects`

| Field | Rule |
|---|---|
| `id` | UUID text primary key |
| `name` | Required, 1-80 characters |
| `original_idea` | Required, preserved exactly |
| `current_playable_version_id` | Nullable pointer; only Promote updates it |
| `active_build_id` | Nullable concurrency guard; only Start/Finish/Recovery updates it |
| `archived_at` | Nullable UTC; archived projects cannot start builds |
| `created_at`, `updated_at` | UTC |

`stage` is not stored. A Project has one current playable pointer and at most one active build guard.

### GameDesign

`game_designs`

One row per Project, unique on `project_id`.

| Field | Rule |
|---|---|
| `id`, `project_id` | UUID primary key and required unique project FK |
| `content_json` | Human-readable design payload |
| `status` | `draft`, `submitted`, `confirmed`, `rejected` |
| `confirmed_at` | Set only by explicit Confirm action |
| `created_at`, `updated_at` | UTC |

Design confirmation is a platform action. A provider result or timer cannot confirm it.

### GameSpecRevision

`game_spec_revisions`

| Field | Rule |
|---|---|
| `id`, `project_id` | UUID primary key and required project FK |
| `revision_number` | Positive, unique per Project |
| `content_json` | Provider-neutral CreatorGameSpec payload |
| `status` | `draft`, `confirmed`, `superseded` |
| `confirmed_at`, `superseded_at` | UTC markers controlled by service |
| `created_at` | UTC |

Confirming a revision marks the previously confirmed revision as `superseded` in the same transaction. The content of a revision is immutable after creation.

### Build

`builds`

| Field | Rule |
|---|---|
| `id`, `project_id` | UUID primary key and required project FK |
| `gamespec_revision_id` | Must refer to a confirmed revision |
| `parent_build_id` | Nullable; set for Retry |
| `attempt` | Positive, increasing for a project build chain |
| `status` | `pending`, `running`, `cancelling`, `succeeded`, `failed`, `cancelled`, `orphaned` |
| `failure_code`, `failure_message` | Sanitized terminal diagnostics |
| `started_at`, `ended_at`, `created_at` | UTC |

There is a partial unique index preventing more than one non-terminal Build per Project. The service also updates `projects.active_build_id` as an explicit, conditional guard so the invariant is visible and recoverable.

### BuildCandidate

`build_candidates`

| Field | Rule |
|---|---|
| `id`, `project_id`, `build_id` | UUID primary key and required foreign keys |
| `status` | Mirrors terminal result: `succeeded`, `failed`, `cancelled`, `orphaned`, or `promoted` |
| `artifact_path`, `artifact_checksum` | Nullable for failures, safe relative paths only |
| `summary` | Sanitized human-readable result |
| `created_at` | UTC |

A Candidate is an unpromoted snapshot. Its creation never changes `current_playable_version_id`.

### PlayableVersion

`playable_versions`

| Field | Rule |
|---|---|
| `id`, `project_id`, `candidate_id` | Immutable UUIDs and required FKs |
| `number` | Increasing and unique per Project |
| `parent_version_id` | Nullable previous playable pointer |
| `test_report_id` | Required opaque ID supplied by the later test-gate Change |
| `git_commit`, `artifact_path`, `artifact_checksum` | Immutable provenance |
| `created_at` | UTC |

Only explicit `promote_candidate()` can create this record and atomically update the Project pointer. C02 does not implement TestReport persistence; it accepts a `PromotionAuthorization` value whose `test_report_id` and `verdict == "pass"` were produced by the later gate contract.

### Release

`releases`

| Field | Rule |
|---|---|
| `id`, `project_id`, `playable_version_id` | Immutable UUIDs and required FKs |
| `number` | Increasing and unique per Project |
| `status` | V1 C02 uses `published` only; future retraction is a separate Change |
| `published_at` | UTC |

`publish_version()` is an explicit human action boundary. Failed, cancelled, orphaned, or unpromoted Candidates cannot create a Release.

## Derived ProjectStage

`derive_project_stage(project_id)` returns a read-only enum using one transaction snapshot and this precedence:

1. `archived` when `archived_at` is set.
2. `building` when `active_build_id` points to a non-terminal Build.
3. `candidate_review` when the latest Candidate is `succeeded` and not `promoted`.
4. `published` when a Release exists for the current PlayableVersion.
5. `playable` when `current_playable_version_id` is present.
6. `ready_to_build` when a current GameSpecRevision is confirmed.
7. `gamespec_review` when a GameSpecRevision exists but no current revision is confirmed.
8. `design_review` when GameDesign is submitted or rejected and needs a human decision.
9. `design_draft` otherwise.

The stage function is deterministic and must not read Vue state, URL flags, provider events, or local fixtures.

## State Transitions

### Design and GameSpec

```text
GameDesign: draft -> submitted -> confirmed
                         └──────> rejected -> submitted
GameSpecRevision: draft -> confirmed -> superseded
```

Only explicit service methods can confirm or reject. A new revision does not alter the previous revision until the new one is confirmed.

### Build

```text
pending -> running -> succeeded
                   -> failed
                   -> cancelling -> cancelled
pending -> cancelled
pending/running/cancelling -> orphaned  (restart recovery)
```

`finish_build()` is idempotent for a terminal Build: repeating the same terminal result returns the existing Candidate and does not create a duplicate. A conflicting terminal result is rejected.

### Candidate and Playable

```text
Candidate(succeeded) --explicit human Promote + PASS authorization--> PlayableVersion
Candidate(failed/cancelled/orphaned) -------------------------------> no Version
```

Promote creates an immutable Version with `parent_version_id = Project.current_playable_version_id`, marks the Candidate `promoted`, and updates the pointer in one transaction. A Candidate never writes the pointer by itself.

### Release

```text
current PlayableVersion --explicit human Publish--> immutable published Release
```

Publishing the same PlayableVersion twice is idempotent or rejected with a stable domain error; it never creates duplicate release numbers.

## Active Build Guard and Concurrency

`start_build()` performs the following inside one transaction:

1. Load Project and require it is not archived.
2. Require the requested GameSpecRevision is confirmed.
3. Create a pending Build with a new ID.
4. Atomically update `projects.active_build_id` only when it is `NULL`.
5. Transition the Build to `running` and commit.

If the conditional update affects zero rows, the service raises `ActiveBuildError`; the attempted Build is rolled back. SQLite's write transaction plus the partial unique index protects the database even when two callers race.

Finishing or cancelling a Build clears `active_build_id` only when the pointer still equals that Build ID. A late completion from an old Build cannot clear a newer guard.

## Failure, Cancel, Retry, and Restart Invariants

- Failed, cancelled, and orphaned Builds retain sanitized diagnostics and their Candidates.
- None of those outcomes creates a PlayableVersion, updates the current playable pointer, or creates a Release.
- Retry creates a new Build with `parent_build_id` pointing to the prior terminal Build. It starts only after the active guard is clear.
- A successful retry still requires explicit Promote; it does not auto-promote.
- Backend startup recovery marks every `pending`, `running`, or `cancelling` Build as `orphaned`, writes a restart failure code, creates no Version, and conditionally clears its Project guard.
- Recovery is idempotent: a second call does not alter terminal Builds or create duplicate Candidates.
- A transaction rollback leaves the Build status, Project pointer, Candidate, Version, and Release changes as they were before the attempted operation.

## Repository / Service Boundary

Repositories expose focused persistence operations:

```text
ProjectRepository
GameDesignRepository
GameSpecRevisionRepository
BuildRepository
BuildCandidateRepository
PlayableVersionRepository
ReleaseRepository
```

They may query, insert, and update records but do not enforce cross-entity transitions. `ProjectLifecycleService` owns:

```text
submit_design()
confirm_design()
create_gamespec_revision()
confirm_gamespec_revision()
start_build()
mark_build_running()
finish_build()
cancel_build()
retry_build()
promote_candidate()
publish_version()
recover_orphaned_builds()
derive_project_stage()
```

No FastAPI route is added in C02. Later Changes can call this service without duplicating state rules.

## Testing Strategy

Tests are repository/service tests against the C01 isolated SQLite fixture:

- migration creates all seven tables, foreign keys, unique constraints, and no unrelated tables;
- design/spec confirmation and immutable revision behavior;
- successful build creates a Candidate but leaves the current playable pointer unchanged;
- explicit Promote creates one immutable PlayableVersion and updates the pointer;
- failed/cancelled/orphaned build leaves playable and Release unchanged;
- one active Build per Project, including a two-session race test;
- finish/cancel/retry idempotency and conflicting terminal result rejection;
- restart recovery is idempotent and clears only matching active pointers;
- cross-Project foreign-key isolation;
- derived stage transitions cover draft → review → ready → building → candidate review → playable → published.

## Migration and Compatibility

C02 adds Alembic revision `0002_project_lifecycle_domain` after C01's empty foundation revision. Existing C01 databases remain upgradeable. No frontend or C01 error contract changes are required. C02's `test_report_id` is intentionally an opaque future contract field, not a C02 table or service.

## Risks and Decisions

- **SQLite concurrency:** conditional update plus a partial unique index is sufficient for the single-process V1 backend; multi-process locking is deferred to deployment work.
- **Stage drift:** no stored stage column means UI cannot accidentally become a second state machine; the trade-off is a derived query that must be tested exhaustively.
- **Test gate dependency:** C02 requires a typed promotion authorization value rather than inventing a TestReport table; C12 owns TestReport persistence and validation.
- **Build execution:** C02 records lifecycle outcomes supplied by a caller; C09/C10/C11 own process execution and orchestration.
