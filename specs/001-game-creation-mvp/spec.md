# Feature Specification: AI 游戏共创平台 V1/V2

**Feature Branch**: `not-created (no before_specify hook)`

**Status**: Draft

**Input**: User description: "先以 OpenGame 建立可运行平台基线，再以 Claude Agent SDK 构建由平台确定性编排的领域 Agent Runtime，使相同工作流能够创建、修改、修复、构建、测试并版本化固定类型的 2D 生存游戏。"

## Clarifications

### Session 2026-08-07

- Q: MVP 在线部署后，项目编辑后台和游戏预览分别采用什么访问控制？ → A: 编辑后台需要统一访问码，游戏预览可公开访问。
- Q: 当同一游戏项目已有生成、修改、保存或恢复任务正在执行时，新的变更请求应该如何处理？ → A: 仅允许一个变更任务，新请求被阻止直到当前任务结束。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从创意生成可玩游戏 (Priority: P1)

作为个人开发者，我希望创建项目并输入一句游戏创意，确认 AI 生成的简版 GDD 和
GameSpec，然后获得包含基础美术、完整生存玩法和可交互 NPC 的浏览器可玩游戏，从而无需
从零搭建工程即可验证创意。

**Why this priority**: 这是结项演示的最短端到端闭环，也是其他编辑、版本和恢复能力存在的
前提。

**Independent Test**: 使用一个全新项目输入一句测试创意，确认 GDD 和 GameSpec 后等待生成
与构建；验证预览中的玩家移动、敌人追踪、生命值、道具、计分、NPC 对话和胜负条件均可用。

**Acceptance Scenarios**:

1. **Given** 用户尚未创建项目，**When** 用户创建项目并输入一句非空游戏创意，**Then** 系统创建唯一项目并生成一份待确认的简版 GDD。
2. **Given** GDD 已生成，**When** 用户查看 GDD，**Then** GDD 展示游戏目标、核心玩法、角色、敌人、道具、NPC、胜负条件和美术风格。
3. **Given** GDD 内容有效，**When** 系统生成 GameSpec，**Then** 用户可以查看并分别确认 GDD 和结构化 GameSpec，未确认前不得开始游戏代码生成。
4. **Given** GDD 和 GameSpec 已确认，**When** 生成任务完成且构建验证通过，**Then** 系统创建成功版本并在浏览器中提供可直接启动的游戏预览。
5. **Given** 游戏预览已启动，**When** 用户完成一次试玩，**Then** 玩家可移动，敌人会生成并追踪玩家，道具可收集，生命值和计分会变化，NPC 可触发对话，且至少一个胜利或失败条件能够触发。

### User Story 2 - 观察并控制 AI 执行 (Priority: P1)

作为等待生成或修改游戏的用户，我希望看到 AI 当前阶段、执行事件和构建日志，并能取消、
重试或恢复长时间任务，从而知道系统正在做什么并能处理失败。

**Why this priority**: 游戏生成是长时间且可能失败的过程；缺少状态、取消和恢复会使核心流程
无法可靠演示或安全操作。

**Independent Test**: 启动一次生成任务，在各阶段检查状态和日志，取消任务并验证项目不受
损；再触发一次可恢复失败，验证错误、重试或恢复路径及最终产物关联。

**Acceptance Scenarios**:

1. **Given** 用户启动生成或修改，**When** 任务开始执行，**Then** 系统展示唯一 run ID、当前阶段、任务状态、开始时间和持续追加的事件或日志。
2. **Given** 任务仍在运行，**When** 用户请求取消，**Then** 系统停止后续执行、标记为“已取消”，并保留取消前的日志且不改变当前可玩版本。
3. **Given** 构建或执行失败，**When** 用户查看任务，**Then** 系统展示失败阶段、可理解的原因、相关错误位置及安全的重试或恢复操作。
4. **Given** 任务失败或被取消，**When** 用户选择恢复，**Then** 系统从最近成功 Version 创建关联的新 run，重新执行原始需求并保留追溯关系，不复用阶段检查点或 Agent 内部状态。

---

### User Story 3 - 使用 AI 增量修改游戏 (Priority: P2)

作为个人开发者，我希望用自然语言修改当前游戏的规则、NPC 或指定素材，让 AI 在现有项目
上增量工作并生成新版本，从而快速迭代创意而不丢失已有成果。

**Why this priority**: 共创平台的核心差异不仅是一次性生成，而是围绕同一个持久项目持续
协作。

**Independent Test**: 在成功游戏版本上依次提出一项规则修改和一项 NPC 修改，验证 AI 读取
当前状态、只修改相关内容、创建新版本，并在重新构建后体现两项变化。

**Acceptance Scenarios**:

1. **Given** 当前存在可玩版本，**When** 用户要求修改玩家、敌人、道具、游戏时间或胜负条件中的受支持参数，**Then** AI 基于当前 GameSpec 和源码增量修改并创建候选版本。
2. **Given** 当前游戏包含 NPC，**When** 用户要求修改 NPC 名称、位置、对话或有限行为，**Then** 新版本仅采用受支持的确定性 NPC 能力且试玩中可验证变化。
3. **Given** 用户指定一个基础美术素材，**When** 用户要求替换或重新生成，**Then** 系统保留素材来源记录并只更新指定素材及必要引用。
4. **Given** 用户请求有限范围内的局部机制或修复构建错误，**When** 请求符合固定游戏模板边界，**Then** 系统执行增量修改；超出边界时明确拒绝并说明第一阶段限制。
5. **Given** AI 修改构建失败，**When** 任务结束，**Then** 失败候选版本保留错误信息，当前可玩版本和预览保持不变。

### User Story 4 - 直接编辑并重新构建 (Priority: P2)

作为具备开发经验的用户，我希望查看项目文件并在网页中直接编辑 GameSpec、NPC 配置和允许
编辑的源码，保存后触发构建，从而在 AI 之外保持对项目的直接控制。

**Why this priority**: AI 与用户必须共同编辑同一个项目；直接编辑是验证项目可控、可继续开发
的重要路径。

**Independent Test**: 修改一个允许编辑的 GameSpec 参数和一个源码行为，保存并构建，验证新
版本、变更摘要、错误定位和成功预览；再提交一个导致构建失败的修改，验证稳定版本未被覆盖。

**Acceptance Scenarios**:

1. **Given** 项目已生成，**When** 用户打开文件视图，**Then** 系统展示项目文件并明确区分可编辑文件与受保护或只读文件。
2. **Given** 用户修改 GameSpec、NPC 配置或允许编辑的源码，**When** 用户保存，**Then** 系统记录用户修改、创建候选版本并触发重新构建。
3. **Given** 用户修改包含可定位错误，**When** 构建失败，**Then** 系统展示相关文件和位置，保留失败修改用于修复，且不更新当前预览。
4. **Given** 用户修复错误并再次保存，**When** 新构建成功，**Then** 系统将新版本设为当前可玩版本并刷新预览。

---

### User Story 5 - 查看历史并恢复稳定版本 (Priority: P2)

作为持续迭代游戏的用户，我希望查看每次首次生成、AI 修改和手工修改产生的 Candidate、成功
Version 及其来源，
并恢复一个构建成功的历史版本，从而可以放心试验并从失败或不满意的修改中返回。

**Why this priority**: 版本化和恢复保护可运行成果，是 AI 与人工共同修改同一项目的安全网。

**Independent Test**: 创建至少三个不同来源且包含成功和失败状态的 Candidate，检查记录完整性，
选择一个历史成功版本恢复，并验证恢复行为本身可追溯且游戏重新可玩。

**Acceptance Scenarios**:

1. **Given** 项目包含多个 Candidate 和 Version，**When** 用户查看历史，**Then** 每条记录展示修改来源、用户需求、修改摘要、修改文件、GameSpec、构建测试状态、创建时间、发布状态和可运行产物状态。
2. **Given** 用户选择一个构建成功的历史版本，**When** 用户确认恢复，**Then** 系统基于该历史状态创建新的恢复版本，不删除其后的历史记录。
3. **Given** 最近一次候选版本失败，**When** 用户返回试玩，**Then** 浏览器仍加载最近一个构建成功的版本。
4. **Given** 用户查看任一版本，**When** 打开追溯信息，**Then** 可以关联其原始创意、GDD、GameSpec、用户要求、AI 与手工修改、素材、运行配置和构建结果。

### User Story 6 - 使用 Claude 领域 Agent Runtime 完成相同闭环 (Priority: P1 for V2)

作为平台开发者，我希望在不改变用户工作流和平台质量门禁的情况下，将 Agent backend 从
OpenGame baseline 切换为 Claude Agent Runtime，从而由 AI Cowork Game 自己的 Planning、Asset、
Coding 和 Test 领域 Agent 完成创建、增量修改、失败修复和可玩版本发布。

**Why this priority**: OpenGame 只负责建立 V1 baseline；Claude Agent SDK Runtime 是最终目标，
只有它能跑通同一平台闭环时 V2 才算完成。

**Independent Test**: 使用 Claude Runtime 从同一条验收创意开始，依次完成 GDD 与 GameSpec
人工确认、素材审阅、Candidate 生成、构建、结构化 playtest、一次故意失败后的修复与重测、
版本发布和增量修改；验证所有平台状态均由确定性工作流推进。

**Acceptance Scenarios**:

1. **Given** 平台选择 Claude Runtime，**When** 用户提交创意，**Then** PlanningAgent 分阶段提交 GDD 和 GameSpec，且每一步只有在人类确认后才能进入下一阶段。
2. **Given** GameSpec 已确认，**When** 工作流进入素材阶段，**Then** AssetAgent 产生可追溯素材清单，且未被平台接受前不得进入正式编码阶段。
3. **Given** 素材已接受，**When** CodingAgent 完成创建或增量修改，**Then** 系统创建 Candidate，而不是直接发布 Version。
4. **Given** Candidate 已构建，**When** TestAgent 执行 playtest，**Then** 其输出必须转换为结构化 TestReport，并由平台根据证据决定 PASS 或 FAIL。
5. **Given** TestReport 为 FAIL，**When** 平台允许修复，**Then** CodingAgent 基于失败证据修复同一变更链路，TestAgent 重新测试，且只有最终 PASS 才能发布 Version。
6. **Given** Claude Runtime 完成一次创建和一次增量修改，**When** 用户查看历史，**Then** 每个 run、Agent session、工具调用、Candidate、TestReport 和 Version 均可追溯。

---

### User Story 7 - 将验证成功的产物作为平台资源复用 (Priority: P1 for V2)

作为平台开发者，我希望把经过验证和人工审阅的 Version、开发经验与素材保存为可复用资源，
让后续兼容项目能够从成功证据出发，而不必重复解决相同问题。

**Why this priority**: 这是 V2 证明领域 Runtime 能积累工程能力的最小闭环，但不能演变为自动
学习系统、模板市场或未经审阅的 Skill 修改。

**Independent Test**: 晋升一个成功 Version 为 Template，保存一个已接受 Asset，并将一条成功
repair 经验设为可用；归档当前活动项目后创建第二个隔离演示项目，复用 Template/Asset，并验证
CodingAgent 能读取该经验及其 PASS 证据。

**Acceptance Scenarios**:

1. **Given** Version 已发布且具有有效 PASS TestReport，**When** 用户批准晋升，**Then** 系统创建与固定 Phaser 生存能力兼容的 Reusable Template，并保留来源 Version 和验证证据。
2. **Given** Asset 已被用户接受且来源与许可信息完整，**When** 用户保存为 Reusable Asset，**Then** 系统保留类型、风格、prompt、来源项目和来源 Version。
3. **Given** 当前项目已归档并顺序创建第二个隔离项目，**When** 用户复用已批准 Template 或 Asset，**Then** 系统复制资源到新项目 Workspace 并记录 ResourceUse，不允许跨项目直接写入。
4. **Given** 成功 development/repair run 具有 PASS TestReport，**When** 用户批准结构化经验，**Then** 经验进入 `available` 状态并可通过只读工具提供给 CodingAgent。
5. **Given** 只有一条成功经验，**When** 系统考虑形成 Formal Skill，**Then** 最多创建待审阅 Skill Candidate，不得自动修改或发布 Skill。

### Edge Cases

- 游戏创意为空、只有空白字符、过长或包含无法映射到固定游戏类型的要求时，系统必须阻止
  执行或给出范围内的简化建议，不得静默生成无关游戏。
- GDD 或 GameSpec 生成内容缺少必填部分、格式无效或彼此矛盾时，系统必须要求修正或重新
  生成，且不得进入代码生成。
- 用户在尚无成功 Version 时首次构建失败，系统必须展示失败 Candidate 和修复入口，并明确当前没有可玩
  预览。
- 用户在任务运行中刷新页面或短暂断线后返回，系统必须能通过 run ID 恢复展示真实状态与
  已记录日志，不得重复启动相同任务。
- 用户连续点击生成、修改、保存、重试或恢复时，同一项目不得出现互相覆盖的并发写入；当前
  变更任务结束前，系统必须禁用或拒绝新的变更请求并提示用户等待，不得将其加入后台队列。
- 用户在 AI 运行期间尝试编辑同一文件时，系统必须阻止冲突写入或要求用户在运行结束后基于
  最新版本重新应用修改。
- 用户取消发生在依赖安装或构建的中间阶段时，系统必须清理未完成执行，保留诊断记录，并
  维持稳定产物不变。
- 用户请求超出固定模板、实时大模型 NPC 或其他排除范围时，系统必须说明限制，不得以不可
  验证的部分实现标记任务成功。
- 指定素材生成或接入失败、来源不明或不具备公开使用条件时，该素材不得进入公开产物；系统
  必须提供重试、替换或受控占位素材路径。
- 预览页面能够加载但出现阻断控制台错误、玩家无法移动、核心循环停滞或胜负条件不可触发时，
  构建不得标记成功。
- 恢复目标的可运行产物丢失或损坏时，系统必须先重新验证或重建，失败时保持当前稳定版本。
- AI 或构建过程意外输出密钥、宿主路径或其他敏感信息时，系统必须阻止其进入公开日志和产物，
  将运行标记为安全失败并保留经过脱敏的诊断信息。
- 未提供或提供错误访问码的访问者尝试进入编辑后台、查看内部日志或触发 AI 运行时，系统必须
  拒绝访问；公开游戏预览不得因此要求登录或暴露后台数据。
- Claude Runtime 中任一 Agent 尝试调用未授权工具、访问其他 Agent 的私有工作上下文、修改平台
  状态或越过 Workspace 边界时，平台必须拒绝调用、记录审计事件并安全终止或降级当前步骤。
- TestAgent 返回 PASS 但缺少必需检查项、证据或真实测试结果时，平台必须将报告判为无效，不能
  发布 Version。
- Claude session 中断、过期或无法恢复时，平台必须保留 run/session 映射和 Candidate；恢复必须
  从最近成功 Version 创建关联的新 run 并重新执行当前需求，不得假装续接原 session 或复用部分工作区。
- 未发布 Version、无 PASS TestReport 的 run、未接受素材或来源/许可不完整的素材不得晋升为可复用资源。
- Template 的 capability profile 与目标项目不兼容时必须拒绝复用；不得借资源复用绕过固定游戏类型和 GameSpec 校验。
- 来源 Version、TestReport 或素材文件丢失时，资源必须变为不可用，不能仅凭描述继续提供给 Agent。
- CodingAgent 只能读取 `available` Experience 的结构化摘要和证据引用，不能读取其他项目的任意源码、日志或 Workspace。
- Experience 被撤销或其 Skill Candidate 被拒绝时，不得删除历史审计记录，也不得继续用于新 run。

## Requirements *(mandatory)*

### Functional Requirements

#### 项目、GDD 与 GameSpec

- **FR-001**: 系统必须允许用户创建一个持久化游戏项目；第一阶段每次仅支持一个用户操作一个游戏项目。
- **FR-002**: 系统必须接受一句非空自然语言游戏创意作为首次生成的起点，并将原始输入永久关联到项目。
- **FR-003**: 系统必须根据创意生成简版 GDD，至少包含游戏目标、核心玩法、角色、敌人、道具、NPC、胜负条件和美术风格。
- **FR-004**: 系统必须将 GDD 转换为结构化且可验证的 GameSpec，并保持 GDD 与 GameSpec 之间的追溯关系。
- **FR-005**: 用户必须能够查看 GDD 和 GameSpec，并在继续生成前分别确认二者。
- **FR-006**: 用户必须能够在确认前要求重新生成或修正 GDD 和 GameSpec；确认后的修改必须作为新的版本化变更处理。
- **FR-007**: 系统必须在 GameSpec 缺少必填字段、字段无效或与固定游戏范围冲突时阻止后续生成，并展示可理解的校验问题。

#### 素材、游戏生成与可玩验证

- **FR-008**: 系统必须为玩家、敌人、道具、至少一个 NPC 和背景生成或接入基础美术素材，并展示素材清单。
- **FR-009**: 系统必须记录每项素材的来源、生成方式和公开使用状态；不能确认可用性的素材不得进入公开游戏产物。
- **FR-010**: 系统必须只生成一种固定的 Phaser 2D 俯视角生存游戏，不得向用户呈现其他模板或游戏类型选择。
- **FR-011**: 生成游戏必须包含玩家移动、敌人生成、敌人追踪、玩家生命值、道具收集、计分，以及至少一个可触发的胜利或失败条件。
- **FR-012**: 生成游戏必须包含至少一个可交互 NPC，其结构化定义包含名称、角色定位、外观、初始位置、基础行为和对话。
- **FR-013**: NPC 行为必须限定为站立、巡逻、逃跑等配置允许的确定性行为，且玩家靠近时能够触发对话。
- **FR-014**: 游戏运行期间不得为 NPC 或其他游戏机制调用大模型。
- **FR-015**: 系统必须自动完成候选版本的依赖准备、类型或生产构建检查、页面启动检查和基础可玩性验证。
- **FR-016**: Candidate 只有在项目文件完整、依赖准备成功、构建通过、页面可启动、无阻断控制台错误、玩家可移动、核心循环可运行且至少一个胜负条件可触发时，才能通过 TestReport 并发布 Version。
- **FR-017**: 构建成功后，用户必须能够直接在浏览器中启动或刷新游戏预览，无需下载并手工运行项目。

#### AI 运行状态与控制

- **FR-018**: 每次 AI 运行必须分配唯一 run ID，并关联到项目、触发它的用户需求、运行时后端、Agent session 和 Candidate。
- **FR-019**: 系统必须展示以下适用阶段：等待处理、规划 GDD、等待 GDD 确认、规划 GameSpec、等待 GameSpec 确认、生成素材、等待素材接受、生成或修改代码、Candidate 创建、安装依赖、构建验证、测试、修复、重测、Version 发布、失败和已取消。
- **FR-020**: 运行详情必须记录并展示当前阶段、运行时后端、Agent 类型与 session、模型、AI 消息、工具调用、构建日志、开始与结束时间、结果、失败原因、生成产物、模型用量和可获取的成本。
- **FR-021**: 运行事件和日志必须按发生顺序持续展示，并在用户离开页面后仍可通过 run ID 找回。
- **FR-022**: 用户必须能够取消等待中或执行中的长时间任务；取消不得改变当前可玩版本。
- **FR-023**: 失败运行必须提供明确错误以及适用的安全重试或恢复操作，并保留原失败记录。
- **FR-024**: 每个项目同一时间只能执行一个会改变项目的生成、AI 修改、用户保存、重试或恢复任务；当前任务结束前，系统必须阻止新变更请求、提示用户等待且不得将请求排队。

#### AI 与用户共同编辑

- **FR-025**: AI 修改和用户直接编辑必须作用于同一个持久化项目、GameSpec、源码集合和版本历史。
- **FR-026**: AI 必须基于当前项目状态执行增量修改；除首次创建或用户明确确认重置外，不得重新生成整个项目来替代修改。
- **FR-027**: 用户必须能够通过自然语言修改玩家生命值、移动速度和攻击能力。
- **FR-028**: 用户必须能够通过自然语言修改敌人数量、速度、生命值和生成频率，以及道具效果、游戏时间和胜负条件。
- **FR-029**: 用户必须能够通过自然语言修改 NPC 名称、位置、对话和受支持的确定性行为。
- **FR-030**: 用户必须能够替换或重新生成指定基础美术素材，而无需重新生成全部素材。
- **FR-031**: AI 必须接受固定模板可承载的局部游戏机制修改和构建错误修复，并明确拒绝超出第一阶段边界的请求。
- **FR-032**: 用户必须能够查看游戏项目文件，并清楚识别 GameSpec、NPC 配置、允许编辑的源码和不可编辑内容。
- **FR-033**: 用户必须能够在网页编辑界面修改并保存 GameSpec、NPC 配置和允许编辑的游戏源码，但不得访问平台服务源码、其他项目或宿主环境。
- **FR-034**: 每次用户保存必须记录修改文件和修改来源、创建候选版本并触发重新构建。
- **FR-035**: 构建日志必须展示可获取的错误文件和位置，使用户能够修改失败候选版本后再次构建。
- **FR-036**: 第一阶段网页编辑能力必须聚焦于查看、编辑、保存和构建，不得扩展为完整在线 IDE。

#### 版本、恢复与追溯

- **FR-037**: 首次生成、每次 AI 修改和每次用户保存源码或 GameSpec 都必须先创建唯一 Candidate；只有通过发布门禁的 Candidate 才创建不可变 Version。
- **FR-038**: 每个 Candidate 和 Version 必须记录修改来源、用户需求、修改摘要、修改文件、GameSpec 快照、运行时与 Agent session、构建测试状态、创建时间和产物状态。
- **FR-039**: 用户必须能够查看 Candidate 与 Version 历史，并区分生成中、待测试、测试失败、修复中、已取消、已发布和恢复产生的记录。
- **FR-040**: 构建失败、测试失败、取消或未完成的 Candidate 不得创建或替换当前可玩 Version 及其预览。
- **FR-041**: 用户必须能够选择一个成功历史 Version 进行恢复；恢复必须先创建 Candidate，重新通过构建测试后发布新 Version，并保留完整历史。
- **FR-042**: 每个版本必须能够追溯到原始创意、GDD、GameSpec、后续用户要求、AI 修改、用户手工修改、素材、Agent 与模型配置、相关 run 和构建结果。
- **FR-043**: 系统必须能够为用户展示某版本产生的原因、相对其来源版本的变化以及修改主体。

#### 隔离、安全、成本与交付

- **FR-044**: AI 的文件修改、依赖准备和命令执行必须发生在该游戏项目专属的受限执行空间中。
- **FR-045**: AI 执行默认不得访问用户主目录、宿主凭证、其他游戏项目、平台服务源码或完成任务不需要的网络资源。
- **FR-046**: API Key 和其他密钥不得出现在生成代码、用户可见构建日志或公开游戏产物中；对用户展示的诊断信息必须脱敏。
- **FR-047**: 平台业务能力必须通过可替换的 `GameAgentAdapter` 契约获得规划、素材、创建、修改、修复、构建、playtest、事件、状态、取消、恢复、产物和错误信息，不得把用户流程绑定到单一后端的专有行为。
- **FR-048**: 每次 Agent 运行必须记录耗时、模型调用次数、重试次数和可获取的成本信息。
- **FR-049**: 系统必须通过统一的部署级访问码保护项目编辑后台、内部日志和 AI 运行操作；成功游戏预览必须可通过公开链接访问且不得暴露后台数据，并提供可重复的部署说明。
- **FR-050**: 2026-08-19 结项汇报前，交付必须包含至少一个稳定演示游戏、从创意到试玩的完整演示、AI 修改、用户直接编辑与重建、NPC 生成或修改、录制好的演示视频和项目说明文档。
- **FR-051**: V1 不得提前实现 V2 多领域 Agent Runtime；整个路线图不得包含 Unity、3D、多种游戏类型或模板、LLM 自由编排、实时大模型 NPC、多人协作、社区或市场、复杂动画、完整音乐生成及复杂账号权限系统。

#### Agent Runtime Roadmap

- **FR-052**: Platform V1 必须使用 OpenGameAdapter 作为 GameAgentAdapter 的首个实现，完成 GameSpec → Coding → Candidate → Build → Test → Version 的纵向闭环并建立 benchmark baseline。
- **FR-053**: Platform V2 必须集成 Claude Agent SDK，使用 Claude Runtime adapter 作为主要后端；只有 OpenGame 可运行不构成 V2 完成。
- **FR-054**: V2 必须提供 PlanningAgent、AssetAgent、CodingAgent 和 TestAgent；每个 Agent 必须具有独立 system instructions、Domain Skills、工具权限、Workspace 访问范围以及结构化输入输出。
- **FR-055**: FastAPI 工作流必须拥有 GDD Confirm、GameSpec Confirm、Asset Accept、Candidate 创建、测试裁决和 Version Publish 等业务状态的唯一控制权，Agent 不得自行推进这些状态。
- **FR-056**: PlanningAgent 必须生成或修订 GDD 与 GameSpec，但不得确认设计、修改游戏源码或发布版本。
- **FR-057**: AssetAgent 必须生成、接入或选择占位素材并记录来源，但不得自动接受素材或发布版本。
- **FR-058**: CodingAgent 必须支持 create game、incremental modify 和 repair，只能修改授权 Workspace 内的游戏文件，且不得自行宣告测试成功。
- **FR-059**: TestAgent 必须支持 build 和 playtest，并输出包含必需检查项、证据、失败原因和 PASS/FAIL 裁决输入的结构化 TestReport；不得修改代码或发布版本。
- **FR-060**: 测试失败时，平台必须能够执行 TestAgent FAIL → CodingAgent repair → TestAgent retest 的受控循环，并限制修复次数、时间和成本。
- **FR-061**: 平台必须持久映射 run、Agent session、Workspace、Candidate、TestReport 和 Version，并把 Claude 原生事件规范化为供应商无关的 RunEvent。
- **FR-062**: OpenGameAdapter 必须在 V2 保留为 fallback、reference backend 和 benchmark baseline；两种 runtime 必须共享平台工作流、GameSpec、Candidate/Version 和测试发布门禁。
- **FR-063**: V2 Agent 只能调用其明确允许的 MCP、平台工具和 Workspace 工具；未授权工具、路径和业务状态修改必须被拒绝并形成审计事件。
- **FR-064**: V1 与 V2 必须作为两个可独立验收的里程碑管理；V1 稳定版本不得被未完成或失败的 V2 集成替换。
- **FR-065**: 2026-08-19 前应尽量完成 V2 全部成功标准；若任一 V2 强制门禁未通过，交付说明必须如实标记为“V2 未完成”并列出证据和剩余项，不得以 OpenGame fallback 冒充 Claude Runtime 完成。
- **FR-066**: OpenGame 与 Claude Runtime 必须使用同一组固定创意、GameSpec、修改请求和测试门禁进行基准对比，至少记录成功状态、总耗时、各阶段耗时、模型调用与成本、repair 次数和 TestReport 结果。

#### Reusable Development Knowledge

- **FR-067**: 平台必须支持由用户将具有有效 PASS TestReport 的成功 Version 人工晋升为 Reusable Template，并记录来源 Version、能力兼容标签、GameSpec schema 版本和验证证据。
- **FR-068**: Reusable Template 只能作为兼容的固定 Phaser 2D 生存游戏起点，不得形成多游戏类型、模板市场或绕过当前模板质量门禁的入口。
- **FR-069**: 平台必须支持将已接受且来源、prompt、风格、类型和许可信息完整的 Asset 保存为 Reusable Asset；未接受素材不得进入资源目录。
- **FR-070**: V2 必须允许归档当前活动项目后顺序创建第二个隔离项目，并把已批准 Reusable Asset 复制到该项目；系统仍只允许一个活动项目和一个运行任务。
- **FR-071**: 平台必须支持从成功 development 或 repair run 创建结构化 Development Experience，至少记录问题、适用条件、采取的修改、涉及文件、来源 run/Version 和 PASS TestReport 证据。
- **FR-072**: Development Experience 只有经过人工审阅并处于 `available` 状态时，才能通过只读平台工具提供给 CodingAgent；每次使用必须记录目标 run 和 experience 版本。
- **FR-073**: 单个成功 Run 不得自动修改 Formal Skill；系统最多创建 `pending_review` Skill Candidate，只有独立审阅和验证后才能晋升。
- **FR-074**: 自动模板提取、向量检索、经验聚类和自动 Skill 晋升属于 stretch goal，不得优先于 V1/V2 核心门禁和 2026-08-19 在线交付。

### Key Entities *(include if feature involves data)*

- **游戏项目（Game Project）**: 用户持续共创的唯一工作对象；关联原始创意、当前成功版本、全部版本、运行和项目文件。
- **简版 GDD**: 人可读的游戏设计摘要；包含目标、玩法、角色、敌人、道具、NPC、胜负条件和美术风格，并作为 GameSpec 的来源。
- **GameSpec**: 游戏规则、实体、NPC、素材引用和胜负条件的结构化表达；可验证、可编辑、可版本化。
- **NPC 配置**: GameSpec 中可独立修改的 NPC 定义；包含身份、外观、位置、有限行为和对话。
- **素材（Asset）**: 玩家、敌人、道具、NPC 或背景的可用美术资源；记录来源、生成方式、使用状态和所属版本。
- **素材审阅（Asset Review）**: 用户对一组素材 draft 的接受或拒绝决定；只有已接受清单可进入编码阶段，Agent 只能提交建议。
- **AI 运行（Run）**: 一次创建、修改或修复执行；具有唯一 run ID、阶段、事件、日志、Agent 与模型信息、用量、成本、错误和产物。
- **项目版本（Version）**: 由通过发布门禁的 Candidate 形成的不可变成功快照；具有来源版本、变更记录、GameSpec、PASS TestReport 和可玩产物。失败或取消的变更只保留为 Candidate。
- **构建结果（Build Result）**: 候选版本的构建与可玩性验证结果；包含状态、日志、错误、检查项及可运行产物引用。
- **可玩产物（Playable Artifact）**: 通过全部成功门禁并可在浏览器启动的游戏版本；失败候选不得覆盖当前产物。
- **Agent Session**: 某一 run 中特定领域 Agent 的执行会话；关联运行时后端、模型、工具权限、Workspace、事件、用量与结果。
- **Agent Invocation**: Agent Session 中一次可计量的模型、工具、构建或 playtest 调用；记录输入输出引用、权限结果、耗时和用量，但不拥有业务状态。
- **Candidate**: 尚未发布的项目变更快照；可经历构建、测试、修复和重测，失败时保留诊断但不能成为当前可玩版本。
- **TestReport**: TestAgent 产生并由平台验证的结构化测试证据；覆盖构建、页面启动、阻断错误、玩家移动、核心循环、NPC 交互和胜负条件。
- **Reusable Template**: 从成功 Version 人工晋升的只读起点快照；带能力兼容标签、来源和验证证据，只服务当前固定游戏类型。
- **Development Experience**: 从成功开发或修复中提炼的结构化工程模式；包含适用条件、行动、结果与 PASS 证据，审阅通过后才能供 CodingAgent 使用。
- **Reusable Asset**: 已接受并保存到平台资源目录的素材；保留类型、风格、prompt、来源、许可和来源 Version。
- **Resource Use**: 某个资源被复制或提供给目标项目/run 的审计记录；用于证明没有隐式跨项目访问。
- **Skill Candidate**: 由一个或多个 Experience 提议形成的待审阅 Skill 草案；不是 Formal Skill，不能自动生效。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在预先准备的有效创意和正常服务条件下，用户能在 20 分钟内从创建项目完成到首次浏览器试玩，无需离开核心流程手工搭建工程。
- **SC-002**: 使用三条不同的验收创意连续执行完整流程时，至少 3 次中有 2 次无需开发人员介入即可产生通过全部可玩性检查的游戏；失败流程均能保留可诊断记录并安全重试。
- **SC-003**: 100% 已发布 Version 均关联有效 PASS TestReport，同时通过页面启动、无阻断错误、玩家移动、核心循环运行和至少一个胜负条件触发验证。
- **SC-004**: 受支持的单项 AI 修改在正常服务条件下可于 10 分钟内生成验证结果，且试玩中能观察到请求的变化。
- **SC-005**: 用户在一次演示中可完成 NPC 对话或行为修改以及一次 GameSpec 或源码直接修改，两次修改均创建独立版本并产生更新后的可玩预览。
- **SC-006**: 运行开始后 5 秒内用户可看到 run ID 和初始状态；状态变化和新增日志在产生后 5 秒内可见；取消确认后 10 秒内任务进入终止或正在安全终止的明确状态。
- **SC-007**: 在构建失败、用户取消和恢复演练中，100% 的失败或中断候选不会改变最近一个成功版本，用户可在 30 秒内重新打开该稳定预览。
- **SC-008**: 抽查任意 10 个版本或全部版本（若少于 10 个），100% 能展示规定的版本字段并追溯到来源需求、相关运行、变更和构建结果。
- **SC-009**: 不熟悉项目代码的目标用户在不接受现场指导的情况下，至少 80% 能完成“查看状态、试玩、提出一次 AI 修改、查看版本历史”四项任务。
- **SC-010**: 结项前从一套记录的初始条件连续完成至少 3 次端到端演示演练，且线上地址、稳定演示游戏、AI 修改、直接编辑重建、NPC 演示、视频和项目文档全部可访问。
- **SC-011**: V1 使用 OpenGame backend 连续完成至少 3 次基线流程，并保存每次耗时、成功率、失败阶段和测试结果，作为 V2 benchmark。
- **SC-012**: V2 使用 Claude Runtime 完成与 V1 相同的一次创建和一次增量修改流程，用户无需改变确认、审阅、预览和版本操作。
- **SC-013**: V2 的一次故意测试失败能够被结构化报告识别，并在限定修复次数内完成 CodingAgent repair、TestAgent retest 和最终 PASS；失败期间当前可玩版本保持不变。
- **SC-014**: 抽查所有 V2 run，100% 可追溯到对应 Agent session、工具权限、Candidate、TestReport 和最终 Version 或失败结果。
- **SC-015**: V2 至少有一个成功 Version 经人工门禁晋升为 Reusable Template，并能初始化一个通过 GameSpec 校验的兼容 Candidate。
- **SC-016**: V2 至少有一个已接受 Asset 保存为 Reusable Asset，并在归档原项目后创建的第二个隔离演示项目中成功复用，来源与 ResourceUse 记录完整。
- **SC-017**: V2 至少有一条成功 development/repair Experience 经审阅进入 `available`，CodingAgent 能读取其结构化内容和 PASS 证据；系统不会自动修改 Formal Skill。

## Assumptions

- 第一阶段面向单个个人开发者的演示与使用场景，不包含注册、组织、角色分级或多人同时编辑；
  编辑后台使用统一部署级访问码，不建立个人账号，游戏预览链接可公开访问。
- “单游戏项目”表示 MVP 产品界面任一时刻只维护一个活动项目，但项目内部必须保留多个版本；
  V2 为验证跨项目复用可归档当前项目并顺序创建第二个隔离演示项目，不提供并发多项目管理。
- 用户具备基本代码阅读能力；网页编辑仅提供项目浏览、文本编辑、保存、错误定位和构建入口。
- 用户拥有稳定网络连接，且生成所需的 AI 与素材服务在演示期间可用；外部服务失败按可重试失败处理。
- AI 对用户请求的支持范围以固定生存游戏模板和结构化 GameSpec 可表达能力为准；范围外请求被明确拒绝。
- GDD 和 GameSpec 采用用户显式确认后再进入首次代码生成的流程；修改阶段无需重复完整确认，但必须展示修改摘要和候选版本。
- 恢复历史成功版本不会改写历史，而是创建一个以选定版本为基础的新版本。
- 可玩性检查可由自动检查与演示验收共同完成；任何未通过项都会阻止候选版本成为当前版本。
- 素材必须具有可追溯且可用于最终在线演示的授权或生成来源；无法确认时使用可公开交付的受控占位素材。
- 具体数据库、部署平台、模型、Agent 内部实现和执行基础设施将在规划阶段基于本规格与 Constitution 决定，本规格不作选择。
- V1 与 V2 共享同一个用户工作流和平台状态机；V2 的四个 Agent 视为受控的领域 profile/session，而非四个独立微服务。
- 默认通过部署配置选择 OpenGame 或 Claude backend，不要求最终用户在产品界面中切换。

## Dependencies

- 可提供结构化文本生成、项目增量修改和执行事件的游戏开发 Agent 能力。
- 可生成或接入并确认公开演示使用权的基础美术素材来源。
- 能够安装游戏项目依赖、执行构建、运行浏览器验证并保存可玩产物的隔离执行能力。
- 能够承载产品界面和游戏预览的在线访问环境，以及演示所需的稳定网络和外部服务额度。
- 可用的 Claude Agent SDK、Claude 模型凭证，以及能够为不同 Agent 限制工具和 Workspace 权限的运行环境。

## Out of Scope

- Unity、3D 游戏和固定 2D 俯视角生存游戏以外的游戏类型或模板。
- LLM 自由决定业务阶段、动态创建未审阅 Agent、将四个领域 Agent 拆成高维护微服务，或将平台业务流程绑定到某一供应商原生事件格式。
- 游戏运行时调用大模型的 NPC、复杂记忆、开放式实时对话和自主决策。
- 多用户协作、社区、作品市场、复杂账号体系和细粒度权限管理。
- 复杂动画系统、完整音乐生成和完整在线 IDE 能力。
- 与核心闭环无直接关系的分布式任务系统、复杂微服务或高维护成本基础设施。
- 自动模板提取、向量数据库或语义检索、经验聚类、自动 Skill 晋升、资源市场和通用知识管理平台。
